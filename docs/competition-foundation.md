# Competition foundation

`supabase/migrations/20260907000100_create_competition_foundation.sql` is the
server-owned foundation for Race To Win competitions. It is intentionally not
applied by this repository task.

## Runtime configuration

Only server code may read these values:

- `SUPABASE_SERVICE_ROLE_KEY` — used by Node route handlers after they derive
  the player from verified Supabase Auth claims. It must never be exposed with
  a `NEXT_PUBLIC_` prefix.
- `WHATSAPP_CLAIM_DESTINATION` — optional destination number in international
  digits-only form. Until it is configured, no claim button is enabled.
- `AD_SSV_PROVIDER` and `AD_SSV_WEBHOOK_SECRET` — reserved for a future
  rewarded-ad provider's server-to-server verification callback. No rewarded
  ad is currently treated as verified and no game result is multiplied or
  continued by this phase.

`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` remain
public connection configuration only. They are not privileged credentials.

## Security boundary

The browser cannot access game sessions, validated runs, rankings, referrals,
rewards, fraud records, provisional winners, prize balances, or payouts via
the Supabase Data API. Those tables have RLS enabled and all grants revoked
from `anon` and `authenticated`.

The service-role client is only imported by server-only modules. Public RPCs
are `SECURITY DEFINER`, use an empty `search_path`, have `PUBLIC`, `anon`, and
`authenticated` execution revoked, and are granted only to `service_role`.
HTTP routes obtain the player ID from `auth.getClaims()`; they do not accept a
browser-provided `user_id`.

## Administrative bootstrap

Before administrative winner/fraud RPCs can operate, add the Race To Win
owner's already-authenticated UUID to `private.admin_users` using a controlled
database-admin workflow. Do not expose a browser route that inserts admin
users. The RPC functions re-check that private role on every call.

## Operational flow

1. A server-finalized `game_sessions` row materializes exactly one
   `validated_runs` row in the same database transaction.
2. Database triggers derive the New York tournament day and Monday week start,
   rebuild per-day Top 7 scores, weekly totals, and server-side tie-break
   vectors.
3. Referral qualification counts only validated runs: three or more per New
   York day across five distinct days. The fifth qualifying day chooses the
   inviter's Share week. Later run/referral review removes the Share from the
   ranking without deleting evidence.
4. Provisional winners are generated by an authorized server operator after a
   week closes. Payout eligibility is still subject to review. The prize
   ledger is append-only and is the only writer of balances.

## Deliberately not active

- A rewarded-ad provider, its SSV/webhook verifier, Extra Life, and 2x Points
  remain inactive. The schema permits one reward claim per session so both
  choices cannot be combined once a verified provider is integrated.
- Referral-link entry/capture UI and an admin dashboard are not included.
  Their backend contracts are `/api/referrals/code`, `/api/referrals/attach`,
  and server-only administrative RPCs.
- No migration is applied to Supabase by this work. Confirm the correct Race
  To Win project and run the reviewed migrations in order before enabling the
  related APIs in production.
